## ADDED Requirements

### Requirement: Надёжная постановка задания при загрузке

Сервис SHALL фиксировать байты оригинала и задание на миниатюру в одной транзакции PostgreSQL. Успешная потоковая загрузка SHALL возвращать `201 Created` с прежним `Location` сразу после фиксации. API SHALL асинхронно отправлять событие через FastStream в RabbitMQ и хранить задание до подтверждения доставки в устойчивую очередь.

#### Scenario: Брокер недоступен при загрузке

- **WHEN** клиент загружает допустимое изображение при недоступном RabbitMQ
- **THEN** API возвращает `201`, оригинал доступен по прежнему адресу, а после восстановления связи задание публикуется из PostgreSQL

#### Scenario: Имя уже занято

- **WHEN** клиент загружает допустимое изображение под занятым именем
- **THEN** API возвращает `409`, сохраняя оригинал и задание победившей загрузки

### Requirement: Формат миниатюры

Воркер FastStream SHALL создавать однокадровый 8-битный PNG до 256 × 256 с сохранением пропорций. Воркер SHALL сохранять размер небольшого изображения и порядок пикселей без применения EXIF. Для APNG SHALL использоваться первый кадр анимации.

#### Scenario: Уменьшение прямоугольного изображения

- **WHEN** воркер получает задание для изображения 640 × 320
- **THEN** он сохраняет PNG размером 256 × 128

#### Scenario: Небольшое анимированное изображение

- **WHEN** воркер получает задание для APNG размером 128 × 64
- **THEN** он сохраняет один первый кадр анимации в PNG размером 128 × 64

### Requirement: Получение миниатюры по имени

`GET /images/{name}/thumbnail` SHALL проверять ключ и имя как на маршруте оригинала. Готовая миниатюра SHALL возвращаться с `200` и `Content-Type: image/png`. При её отсутствии API SHALL возвращать `404`, добавляя `Retry-After: 1` только для задания в обработке. Ответы `200` и `404` SHALL содержать `Cache-Control: no-store`.

#### Scenario: Миниатюра в обработке

- **WHEN** клиент с верным ключом запрашивает ещё не готовую миниатюру
- **THEN** API возвращает `404` с `Retry-After: 1`

#### Scenario: Ключ отсутствует

- **WHEN** клиент запрашивает миниатюру без верного ключа
- **THEN** API возвращает `401`

#### Scenario: Оригинал сохранён до миграции

- **WHEN** клиент с верным ключом запрашивает миниатюру оригинала, сохранённого до миграции
- **THEN** API возвращает `404` без `Retry-After`, а исходные байты доступны на прежнем маршруте

### Requirement: Повторы и удаление

Событие SHALL идентифицировать конкретную загрузку. Воркер SHALL подтверждать сообщение после записи миниатюры, окончательного завершения задания при ошибке декодирования или проверки, что запись уже готова либо удалена. Повторная доставка SHALL оставлять готовую миниатюру прежней. Удаление SHALL атомарно удалять оригинал, готовую миниатюру и ожидающее публикации задание. Воркер SHALL игнорировать события для удалённых загрузок, включая доставку после повторного использования имени.

#### Scenario: Повторная доставка

- **WHEN** воркер повторно получает событие для готовой миниатюры
- **THEN** миниатюра остаётся прежней и событие подтверждается

#### Scenario: Удаление во время генерации

- **WHEN** оригинал удаляется и под тем же именем сохраняется другой файл до завершения старого задания
- **THEN** старое задание завершится без записи, а миниатюра новой загрузки будет построена из её собственных байтов


### Requirement: Обработка ошибок воркера

При временной ошибке записи воркер SHALL вернуть сообщение в очередь. При окончательной ошибке декодирования воркер SHALL завершить задание и сохранить доступ к оригиналу.

#### Scenario: PostgreSQL отклоняет временно невозможную запись

- **WHEN** воркер построил PNG, но PostgreSQL не сохранил результат
- **THEN** воркер возвращает сообщение в очередь для повтора

#### Scenario: Pillow не может декодировать неизменяемый оригинал

- **WHEN** воркер получает окончательную ошибку декодирования
- **THEN** воркер завершает задание, маршрут миниатюры возвращает `404` без `Retry-After`, а оригинал по-прежнему доступен
