# Design

## Context

Загрузка уже читает поток с лимитами и проверяет его в рабочих потоках AnyIO. PostgreSQL содержит оригиналы и outbox миниатюр. RabbitMQ подтверждает отправку, FastStream получает события по UUID.

## Decisions

1. **Временное хранение в PostgreSQL.** В том же `INSERT`, который резервирует имя и назначает UUID, сервер сохраняет проверенные байты в `staged_content` и выставляет `event_pending`. API возвращает `202` после фиксации и даёт `Location: /uploads/{uuid}`. До записи оригинала его адрес возвращает `404`. Проверки ключа, имён, форматов и лимитов выполняются при запросе. В RabbitMQ передаётся UUID.
2. **Две очереди и один outbox.** Для строки с пустым `content` издатель выбирает `image.store`, для опубликованного оригинала — `image.thumbnail`. После подтверждения издатель снимает флаг только у той фазы, для которой он отправлял событие. Воркер атомарно переносит байты из `staged_content` в `content` и выставляет флаг для миниатюры. Подтверждение сообщения следует за фиксацией. Старый или повторный UUID безопасен.
3. **Статус и удаление.** Защищённый `GET /uploads/{uuid}` возвращает `pending` или `stored` и адрес оригинала. При удалении имя освобождается, а статус старого UUID становится недоступен. Ошибка миниатюры хранится отдельно и сохраняет статус записанного оригинала.
4. **Миграция.** Существующие оригиналы и незавершённые задания миниатюр сохраняются. При откате миграции ожидающие оригиналы переносятся в `content` до удаления промежуточного столбца.

## Trade-offs

Временные и итоговые байты хранятся в одной базе. При недоступности брокера число принятых загрузок растёт. После публикации ещё необработанное событие зависит от сохранности тома RabbitMQ.
